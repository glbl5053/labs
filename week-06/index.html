Week 06 · Workshop

A tiny agent.

Build a very small AI agent, watch it work, and find the ways it goes wrong. Then look for the same parts in a real one. No coding experience is expected.

What is an agent?

A language model that uses tools in a loop to work toward a goal, until it is finished or stopped.

Last week you sent one request to a model and got one reply. An agent is a program that makes that call again and again. Each time, the model writes what it wants done next. The program does it, adds the result to the list of messages, and calls the model again.

The model can only write text. It cannot open a file or send an email. The program around it, often called the harness, carries out each request, and decides which requests it will carry out at all.

Every agent has four parts: a model that chooses the next step, tools it can ask for, a memory that is the growing list of messages, and limits set by people. Today you will see all four in about thirty lines of program.

What to watch for

Four things the notebook lets you see for yourself.

  1. The model does not wait. Asked to request one tool and stop, it often carries on and writes a result it could not know. The program has to cut the reply short.
  2. The model chooses, the program carries out. Nobody tells the agent which file to open. When you play the program by hand, you make no decisions at all.
  3. A finished run is not a correct one. The loop stops when a line starts with ANSWER. A small model can produce that line with nonsense after it.
  4. Anything the agent reads can try to instruct it. A note in a file reaches the model the same way your question does. Some models obey it, some ignore it silently, and some tell you.

Part C · on your own computer

Codex, on a folder of your own

You have used Codex already. This time, watch how it works as well as what it produces.

Steps

Give it one small job, then read its record.

  1. Make a practice folder holding copies of three or four documents. Do not point an agent at a folder you cannot afford to have changed.
  2. Give Codex one job in that folder. For example: read these documents and write a one-page comparison as a new file.
  3. Find the four parts. Which model is it using? Which tools does it use? Where is its memory: is there an AGENTS.md file, and what does the session show? What are its limits: what is the approval setting, and what happens when it wants to step outside the folder?
  4. Note every question it asks you, and what it did without asking.
  5. Read the record with four questions. What did it read? What did it change? What is the result based on? How did it stop?

What to bring back

Two records and one sentence.

From any part of the lab, keep one record that went well and one that went wrong. A short excerpt is enough. Add a sentence on what made the difference.

Why this is in a policy course

Three questions you can ask without seeing any code.

What can it touch? Which tools does the system have? Do they only look, or can they change things? On whose accounts and files?

Who says yes? Which actions wait for a person, and which do not? Who is that person, and what are they shown before they agree?

What record does it leave? Afterwards, can someone work out what it read, what it did, and why it stopped? Who keeps that record?

These are the tools, the limits and the memory of today's tiny agent, asked from the outside. They apply the same way to a coding assistant, a customer-service system, or a proposal to automate casework in a ministry.
